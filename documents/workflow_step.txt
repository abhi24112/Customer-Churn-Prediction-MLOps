            DVC = pipeline

    - DAG runs: dvc repro -f db_snapshot && dvc repro training
    - DAG structure: dvc pull → db_snapshot → training → dvc push

8. PostgreSQL Setup (Source of Truth for Data)
    - Install PostgreSQL (local via docker-compose or cloud RDS/Azure)
    - Postgres is the live data store, NOT csv files
    - Architecture:
        Postgres → db_snapshot (DVC stage) → snapshot CSV → DVC pipeline
    
    Steps:
        docker-compose up -d  (starts postgres:16-alpine on localhost:5433)
        
    One-time bootstrap (load Kaggle CSV into Postgres):
        $env:DATABASE_URL='postgresql://postgres:postgres@localhost:5433/churn'
        python -m backend.scripts.load_csv_to_postgres
        
    Add rows to Postgres (for new data):
        from backend.postgres import insert_row
        row = {"col1": "val1", "col2": "val2", ...}
        insert_row("churn_raw", row)

9. DVC Pipeline Update (Postgres Integration)
    - New `db_snapshot` stage added to dvc.yaml
    - Flow: Postgres → src/data/raw_data/data.csv → preprocessing → training
    - Why: DVC can't detect DB changes automatically, so snapshot exports current state
    
    Key files:
        backend/postgres.py : connection + insert helpers
        src/pipelines/db_snapshot_pipeline.py : exports Postgres → CSV
        src/components/data_ingestion.py : reads from snapshot (cross-platform paths)
    
    DVC stages now:
        db_snapshot → data_preprocessing → training
        (use `-f` to force snapshot refresh when DB changes)

13. Airflow Daily Operations (astro dev start)
    - DAG: Customer_Churn_DVC_pipeline
    - Schedule: @daily (runs every day at UTC midnight)
    - Tasks:
        dvc_pull_data → run_dvc_pipeline (db_snapshot + training) → dvc_push_result
    
    Workflow each day:
        1. Pull latest code + data from DVC remote
        2. Force refresh snapshot from Postgres
        3. Run preprocessing + training
        4. Push new models/metrics to remote
    
    Monitoring:
        Airflow UI: http://localhost:8080
        Check logs if DAG fails
        Verify dvc.lock updates after each run

    - Next DAG run automatically:

        Reruns preprocessing if snapshot changed

        Pushes new artifacts

16. Conditional Retraining & Drift Monitoring (Evidently AI)
    - Goal: Retrain only when data drifts, not on every schedule.
    - Components:
        src/drift_detection/evidenly_monitoring.py : Runs drift check, returns True/False.
        dags/conditional_retraining_logic.py : Airflow DAG with branching.
    
    Workflow:
        1. Snapshot & Preprocessing (DVC)
        2. check_drift (BranchPythonOperator)
        3. if drift: run_retraining (dvc repro training)
        4. else: skip_retraining (EmptyOperator)

    Benefits:
        - Saves compute costs.
        - Ensures model is always fresh but not over-trained.
        - Event-driven MLOps architecture.
